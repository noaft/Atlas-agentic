# MCP onboarding and explicit inspection

The user authorized MCP as the next feature: add a connection in Settings, check it, see its tools and use it in chat. Execute inline without another approval round, following the existing proposed MCP architecture and the user's preference for simple controls.

## Scope and boundaries

- Add new HTTP/stdio servers only; no overwrite, edit, rename or removal of existing server identities in this feature. This avoids changing live OAuth identities. Preserve all existing server text/comments byte-for-byte by validated append under a file lease, with optimistic whole-document fingerprints and same-directory atomic publication. Reject unsupported/malformed documents and symlink/special-file leaves. Reads/writes bounded to 1 MiB, private Unix creation modes and bounded lock wait. No new dependencies needed.
- Keep user-local config resolution (ATLAS_MCP_CONFIG, ATLAS_CONFIG_DIR, platform config), never workspace config. Reading status and saving config never launches processes, opens browsers or makes server requests. Expose path, fingerprint and credential status from one parsed snapshot.
- Add a Settings-only typed Check tools operation using the existing mcp_list_tools registry authorization and execution path, never business tools. Derive saved conversation workspace/mode from metadata, ignore conflicting frontend paths. Draft operations capture selected workspace/mode. Ask/Workspace use existing ToolRisk/AuthorizationRequest concepts with a Settings-owned operation/channel/approval. Full access preserves existing semantics. No model configuration required.
- Inspection captures config fingerprint/workspace/operation identity, uses short-lived connections, retains existing pagination/byte/tool limits, and closes transports afterward. No automatic probing/retry/replay. Cancellation before approval creates no connection; cancellation during bounded RPC suppresses all late results, with UI remaining Cancelling until worker exit. Each inspection RPC timeout is capped at 30 seconds; cancellation stops further RPCs/pages after the current bounded request.
- Config/context changes invalidate prior check results. Session navigation cancels only owned Settings checks, never chat approvals or global OAuth operations. No backend log may contain arguments, raw protocol bodies, credentials or endpoints.
- UI: one Add connection disclosure; HTTP name/URL or local name/program/one-argument-per-line. Advanced timeout and optional public OAuth registration fields collapsed. Config drafts/focus persist through status refresh. Cards distinguish Authorized/Sign-in required/No sign-in needed from Not checked/Checking/Verified/Failed. Tools and recovery details collapsed. Existing Connect/Cancel/Disconnect recovery remains, with labels making sign-in semantics explicit.

## Acceptance

Tests for validated append/comment preservation, no overwrite, stale roots/fingerprints, invalid/oversized/symlink inputs, private modes, lease conflict; inspection denial/no process, actual stdio/HTTP discovery, bounds and cleanup; saved workspace/mode authority; Settings-only approval/cancel and late callbacks; drafts/focus across async status changes. Run repository checks, render the actual UI in browser, and commit the completed feature locally. Do not push without a new user request.
